A complete guide for setting up SSH keys, managing multi-key configurations, sharing keys across dual-boot/multi-OS environments, and troubleshooting connection and host key errors.

<Aside type="note" title="Quick Summary">
  - **Modern Standard:** Use **Ed25519** (`ssh-keygen -t ed25519`) for faster, more secure keys.
  - **Multi-Key Setup:** Use `~/.ssh/config` with `IdentitiesOnly yes` and custom `Host` aliases to route different keys to the same IP or domain.
  - **Host Key Warning Fix:** Run `ssh-keygen -R <ip-or-domain>` to clear outdated host key fingerprints when a remote server's OS changes.
</Aside>

## 🔑 Part 1: Key Generation & Initial Setup

### 1. Generating SSH Keys

Ed25519 is the modern standard for SSH keys, offering superior security and performance compared to RSA.

<Tabs>
  <TabItem label="Ed25519 (Recommended)">
    ```bash
    # Generate an Ed25519 key pair with a descriptive comment
    ssh-keygen -t ed25519 -C "your_email@example.com"
    ```
    - **Private key location:** `~/.ssh/id_ed25519`
    - **Public key location:** `~/.ssh/id_ed25519.pub`
  </TabItem>

  <TabItem label="RSA (Legacy Compatibility)">
    If connecting to legacy systems that do not support Ed25519, generate a 4096-bit RSA key:
    ```bash
    ssh-keygen -t rsa -b 4096 -C "your_email@example.com"
    ```
  </TabItem>
</Tabs>

### 2. Copying Public Key to Remote Server

To enable passwordless authentication, your **public key** (`.pub`) must be appended to `~/.ssh/authorized_keys` on the target remote server.

<Tabs>
  <TabItem label="Linux / macOS / Git Bash">
    ```bash
    # Automatically copy your default public key to the remote server
    ssh-copy-id user@192.168.1.105

    # Copy a specific key file
    ssh-copy-id -i ~/.ssh/id_ed25519_custom.pub user@192.168.1.105
    ```

  </TabItem>

  <TabItem label="Windows PowerShell (Manual Copy)">
    If `ssh-copy-id` is not available in Windows PowerShell, pipe your public key over SSH:
    ```powershell
    cat ~/.ssh/id_ed25519.pub | ssh user@192.168.1.105 "mkdir -p ~/.ssh && chmod 700 ~/.ssh && cat >> ~/.ssh/authorized_keys && chmod 600 ~/.ssh/authorized_keys"
    ```
  </TabItem>
</Tabs>

### 3. File Permissions Requirement (Linux Server)

SSH strictly enforces file permission security on the target server. Incorrect permissions will cause `Permission denied (publickey)` errors.

| Path                     | Required Permission | Command                            |
| :----------------------- | :------------------ | :--------------------------------- |
| `~/.ssh` directory       | `700` (`rwx------`) | `chmod 700 ~/.ssh`                 |
| `~/.ssh/authorized_keys` | `600` (`rw-------`) | `chmod 600 ~/.ssh/authorized_keys` |
| Private keys (`id_*`)    | `600` (`rw-------`) | `chmod 600 ~/.ssh/id_ed25519`      |
| Public keys (`id_*.pub`) | `644` (`rw-r--r--`) | `chmod 644 ~/.ssh/id_ed25519.pub`  |

## 🎛️ Part 2: Managing Multiple Keys & Addresses (`~/.ssh/config`)

You can easily use **multiple distinct SSH keys for the exact same IP address or domain**. The SSH client handles this via `~/.ssh/config` using **Host Aliases**.

### 1. Multiple Keys for the Same IP / Server

If you have a server (`192.168.1.105`) where you log in as different users or perform different administrative roles (e.g., general admin vs automation/backup):

```ini
# Identity 1: Main Admin User
Host server-admin
    HostName 192.168.1.105
    User toni
    IdentityFile ~/.ssh/id_ed25519_admin
    IdentitiesOnly yes

# Identity 2: Automated Backup User on the SAME IP
Host server-backup
    HostName 192.168.1.105
    User backupuser
    IdentityFile ~/.ssh/id_ed25519_backup
    IdentitiesOnly yes
```

- Connecting with `ssh server-admin` logs in as `toni` using `id_ed25519_admin`.
- Connecting with `ssh server-backup` logs in as `backupuser` using `id_ed25519_backup`.

<Aside type="caution" title="Why 'IdentitiesOnly yes' is essential">
  By default, SSH tries every loaded key in your `ssh-agent` sequentially. If you have many keys,
  the target server will reject the connection with `Too many authentication failures` before
  reaching the correct key. `IdentitiesOnly yes` forces SSH to ONLY present the key specified in
  `IdentityFile`.
</Aside>

### 2. Multiple Accounts for the Same Service (GitHub / GitLab)

To route different keys to the same domain (e.g., personal vs work GitHub accounts):

```ini
# Personal GitHub Account
Host github.com-personal
    HostName github.com
    User git
    IdentityFile ~/.ssh/id_ed25519_personal
    IdentitiesOnly yes

# Work GitHub Account
Host github.com-work
    HostName github.com
    User git
    IdentityFile ~/.ssh/id_ed25519_work
    IdentitiesOnly yes
```

**Git Usage:**

```bash
# Clone personal repo using alias
git clone git@github.com-personal:username/personal-repo.git

# Clone work repo using alias
git clone git@github.com-work:company/work-repo.git
```

### 3. Essential SSH Config Reference

| Directive               | Description                                            | Example                            |
| :---------------------- | :----------------------------------------------------- | :--------------------------------- |
| `Host`                  | Nickname or wildcard pattern for the connection        | `Host myserver`                    |
| `HostName`              | Actual IP address or domain name                       | `HostName 192.168.1.105`           |
| `User`                  | Remote SSH login username                              | `User root`                        |
| `Port`                  | Custom SSH port (default is 22)                        | `Port 2222`                        |
| `IdentityFile`          | Path to specific private key file                      | `IdentityFile ~/.ssh/id_ed25519`   |
| `IdentitiesOnly`        | Prevents trying default/agent keys (`yes`/`no`)        | `IdentitiesOnly yes`               |
| `StrictHostKeyChecking` | Host key verification mode (`accept-new`, `yes`, `no`) | `StrictHostKeyChecking accept-new` |

## 🔀 Part 3: Dual-Boot & Multi-OS Setup Solutions

When a target PC or server runs **multiple OS installations** (dual-boot Linux/Windows or multiple distros), or when your local PC dual-boots, SSH keys can trigger conflicts. Here is how to handle each scenario cleanly.

### 1. Server-Side Multi-OS (Preventing Host Key Conflicts)

**The Problem:** Each time you install or boot a different OS on the same server machine (`192.168.1.105`), OpenSSH server generates a _new host key_. When you try to connect, your client detects a fingerprint change and throws `WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!`.

<Steps>
1. **Solution A: Synchronize Host Keys Across Server OSes (Recommended)**
    
    Copy the host private and public keys from OS A to OS B on the server so both OS instances share the same identity:
    ```bash
    # On Server OS B, copy keys from OS A into /etc/ssh/
    sudo cp /path/to/os_a/etc/ssh/ssh_host_ed25519_key* /etc/ssh/
    sudo chmod 600 /etc/ssh/ssh_host_ed25519_key
    sudo chmod 644 /etc/ssh/ssh_host_ed25519_key.pub
    sudo systemctl restart sshd
    ```
2. **Solution B: Auto-Accept New Keys via Client SSH Config**
    If synchronization isn't feasible, tell your client to accept new keys for your local trusted home server IP without blocking:

    ```ini
    Host 192.168.1.105 home-server
        HostName 192.168.1.105
        StrictHostKeyChecking accept-new
    ```

</Steps>

### 2. Client-Side Multi-OS (Sharing & Authorizing Client Keys)

If your local client workstation dual-boots Windows and Linux:

- **Option A: Single Key Pair across OSes.** Copy your private key (`id_ed25519`) and public key (`id_ed25519.pub`) between your Windows `C:\Users\Toni\.ssh\` folder and Linux `~/.ssh/` directory.
- **Option B: Distinct Key Pair per Client OS.** Keep unique keys for Windows (`id_ed25519_win`) and Linux (`id_ed25519_linux`), and add **both public keys** to the server's `~/.ssh/authorized_keys` file:

```bash
# Server ~/.ssh/authorized_keys file containing multiple authorized client public keys
ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAI... toni-windows-pc
ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAI... toni-linux-laptop
```

## 🛠️ Part 4: Troubleshooting & Diagnostics

### 1. `WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!`

```text
@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
@    WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!     @
@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
IT IS POSSIBLE THAT SOMEONE IS DOING SOMETHING NASTY!
Offending ED25519 key in /c/Users/Toni/.ssh/known_hosts:8
Host key verification failed.
```

**Why it happens:** The target server's host key changed (OS reinstallation, dual-boot switch, or hardware swap).

**Resolution:**

```bash
# Remove the old cached host fingerprint for the IP/domain
ssh-keygen -R 192.168.1.105

# Connect again and accept the new key fingerprint
ssh user@192.168.1.105
```

### 2. `Permission denied (publickey)`

If SSH fails to connect:

1. Verify the public key is in `~/.ssh/authorized_keys` on the remote server.
2. Fix server permissions: `chmod 700 ~/.ssh && chmod 600 ~/.ssh/authorized_keys`.
3. Check that the client is sending the correct key by testing with verbose output:
   ```bash
   ssh -vvv user@192.168.1.105
   ```
   Look for lines starting with `debug1: Offering public key:` to verify which key is being offered.

### 3. Managing the SSH Agent

If your key has a passphrase, add it to `ssh-agent` so you only enter the passphrase once per session:

```bash
# Start ssh-agent in current shell
eval "$(ssh-agent -s)"

# Add your private key to agent
ssh-add ~/.ssh/id_ed25519

# List currently loaded keys in agent
ssh-add -l
```
