## 🚀 Strategy 1: Build in GitHub Actions & Sync `dist/` to Host

For static site generators like **Astro**, offloading the `pnpm build` process to GitHub's free runners saves home server CPU and RAM. Once built, only the generated `dist/` directory is synced over SSH to the server's web root.

Switching to GitHub-hosted runners means the build now happens on a throwaway GitHub VM, so getting files onto `neuromancer` requires SSH. Here's how to do it while keeping the same hardened posture as the rest of your setup (key-only, no root, minimal blast radius).

### 1. Create a dedicated, restricted deploy user

Don't reuse `toni` or reuse `ghrunner` as-is (it's `nologin`, which is fine — but let's be explicit about what this account can do). A deploy account should be able to **log in via SSH key only**, and ideally be restricted to _only_ running the deploy command, not a general shell:

```bash
sudo adduser --system --shell /bin/bash --home /srv/deploy/raknadocs --group deploy-raknadocs
sudo usermod -aG webdeploy deploy-raknadocs
```

Note it needs `/bin/bash` (not `nologin`) since it's now doing an actual SSH login — but we'll lock down what that login can do in step 3.

### 2. Generate a dedicated deploy keypair

Generate this **on your machine**, not on the server — the private half goes into GitHub Secrets, never onto disk on `neuromancer`:

```bash
ssh-keygen -t ed25519 -f ~/deploy_raknadocs_key -C "gh-actions-deploy-raknadocs" -N ""
```

This gives you `deploy_raknadocs_key` (private) and `deploy_raknadocs_key.pub` (public).

### 3. Install the public key, restricted to one command

```bash
sudo mkdir -p /srv/www/raknadocs_gh/.ssh
sudo tee /srv/www/raknadocs_gh/.ssh/authorized_keys > /dev/null <<'EOF'
command="rsync --server -logDtprze.iLsfxC --delete . /srv/www/raknadocs_gh/",no-port-forwarding,no-X11-forwarding,no-agent-forwarding,no-pty ssh-ed25519 AAAA....YOUR_KEY_HERE gh-actions-deploy-raknadocs
EOF

sudo chown -R deploy-raknadocs:deploy-raknadocs /srv/www/raknadocs_gh/.ssh
sudo chmod 700 /srv/www/raknadocs_gh/.ssh
sudo chmod 600 /srv/www/raknadocs_gh/.ssh/authorized_keys
```

The `command="..."` forced-command is the important part: even if this key were ever leaked, it can **only** run that exact `rsync` invocation — no interactive shell, no arbitrary commands, no port forwarding. Paste your real public key content in place of the placeholder.

### 4. Add the private key + host details to GitHub Secrets

In the repo's **Settings → Secrets and variables → Actions**, add:

- `DEPLOY_SSH_KEY` — contents of `deploy_raknadocs_key` (private key)
- `DEPLOY_HOST` — `YOUR_SERVER_ADDRESS_HERE`
- `DEPLOY_USER` — `deploy-raknadocs`

### 5. Workflow

```yaml
name: Build and Deploy
on:
  push:
    branches: [main]

jobs:
  build-and-deploy:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout Code
        uses: actions/checkout@v7

      - name: Install pnpm
        uses: pnpm/action-setup@v6
        with:
          version: 11

      - name: Setup Node.js
        uses: actions/setup-node@v6
        with:
          node-version: 24
          cache: "pnpm"

      - name: Install Dependencies
        run: pnpm install --frozen-lockfile

      - name: Build Static Site
        run: pnpm build

      - name: Deploy via rsync over SSH
        env:
          SSH_KEY: ${{ secrets.DEPLOY_SSH_KEY }}
        run: |
          mkdir -p ~/.ssh
          echo "$SSH_KEY" > ~/.ssh/deploy_key
          chmod 600 ~/.ssh/deploy_key
          ssh-keyscan -H ${{ secrets.DEPLOY_HOST }} >> ~/.ssh/known_hosts

          rsync -avz --delete -e "ssh -i ~/.ssh/deploy_key" \
            ./dist/ \
            ${{ secrets.DEPLOY_USER }}@${{ secrets.DEPLOY_HOST }}:/srv/www/raknadocs_gh/
```

### 6. Firewall implications

Since GitHub-hosted runners use a huge, constantly-changing range of IPs, you can't allowlist them in `ufw` the way you might for a fixed IP. That's fine — your security here rests on:

- Key-only auth (already your setup)
- The **forced command** restricting this specific key to one harmless operation
- Fail2ban still protecting against brute-force attempts on the SSH port generally

If you want extra isolation, you could restrict this specific user further in `sshd_config` with a `Match User` block:

```
Match User deploy-raknadocs
    PasswordAuthentication no
    AllowTcpForwarding no
    X11Forwarding no
    PermitTTY no
```

This is redundant with the `authorized_keys` restrictions but adds defense-in-depth at the daemon level too.

## ⚡ Strategy 2: GitHub Actions + Self-Hosted Runner

<Aside>
  [Setup user and group for the runner](/reference/user-management/#github-runner-user-setup)
</Aside>

A **Self-Hosted Runner** runs directly on your home server host. It polls GitHub securely via outbound HTTPS, eliminating the need to expose SSH ports or create firewall rules.

<Steps>

1. **Register the Runner on Host Server**
   Navigate to your GitHub Repo -> **Settings** -> **Actions** -> **Runners** -> **New self-hosted runner** and run the provided setup commands:

   ```bash
   # Create a folder
   mkdir -p /srv/runners/gh-raknage && cd /srv/runners/gh-raknage

   # Download the latest runner package
   curl -o actions-runner-linux-x64-2.336.0.tar.gz -L https://github.com/actions/runner/releases/download/v2.336.0/actions-runner-linux-x64-2.336.0.tar.gz

   # Extract the installer
   tar xzf ./actions-runner-linux-x64-2.336.0.tar.gz

   # Fix permissions
   sudo chown -R ghrunner:webdeploy /srv/runners
   sudo find /srv/runners -type d -exec chmod 2775 {} \;   # rwxrwsr-x, SGID
   sudo find /srv/runners -type f -exec chmod 764 {} \;    # rwxrw-r--

   # Configure the runner with repository URL and token
   sudo -u ghrunner ./config.sh --url https://github.com/Raknage/RaknaDocs --token <YOUR_TOKEN>

   # Install as background systemd service as the ghrunner user
   sudo ./svc.sh install ghrunner
   sudo ./svc.sh start
   ```

2. **Self-Hosted Workflow (`.github/workflows/deploy.yml`)**

   ```yaml
   name: Self-Hosted Deploy

   on:
     push:
       branches: [main]
     # Allows you to run this workflow manually from the Actions tab on GitHub.
     workflow_dispatch:

   jobs:
     deploy:
       runs-on: self-hosted
       steps:
         - name: Checkout Code
           uses: actions/checkout@v7
           with:
             ref: main

         - uses: voidzero-dev/setup-vp@v1
           with:
             cache: true
             run-install: true

         - run: |
             vp run vp_build
             rsync -avz --delete dist/ /srv/www/raknaDocs/
   ```

</Steps>

## 🔑 Strategy 3: GitHub Actions + SSH Remote Execution

For executing remote shell commands directly on your home server (e.g., pulling code, reloading systemd services, or updating container stacks) from GitHub Actions.

### Workflow Configuration (`.github/workflows/deploy-ssh.yml`)

```yaml
name: Remote SSH Deployment

on:
  push:
    branches: [main]

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - name: Execute Remote SSH Commands
        uses: appleboy/ssh-action@v1.0.3
        with:
          host: ${{ secrets.SERVER_IP }}
          username: ${{ secrets.DEPLOY_USER }}
          key: ${{ secrets.SSH_PRIVATE_KEY }}
          script: |
            cd /srv/www/raknaDocs
            git pull origin main
            pnpm install --frozen-lockfile
            pnpm build
            sudo systemctl reload caddy
```

## 🔍 Strategy 4: GitHub CI Preview Deployments (Pull Requests)

Preview deployments allow you to test changes on every Pull Request before merging to `main`. On PR creation or updates, GitHub Actions builds the preview site and deploys it to a dedicated subpath (e.g., `docs.example.com/previews/pr-12`).

### 1. PR Preview Build Workflow (`.github/workflows/pr-preview.yml`)

```yaml
name: Deploy PR Preview

on:
  pull_request:
    types: [opened, synchronize, reopened]

jobs:
  deploy-preview:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v3
        with:
          version: 9
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: "pnpm"

      - run: pnpm install --frozen-lockfile
      - run: pnpm build --base /previews/pr-${{ github.event.number }}/

      - name: Deploy Preview Artifacts
        uses: easingthemes/ssh-deploy-5.5@v4
        with:
          SSH_PRIVATE_KEY: ${{ secrets.SSH_PRIVATE_KEY }}
          REMOTE_HOST: ${{ secrets.SERVER_IP }}
          REMOTE_USER: ${{ secrets.DEPLOY_USER }}
          SOURCE: "dist/"
          TARGET: "/srv/www/raknaDocs/previews/pr-${{ github.event.number }}"
          ARGS: "-avz --delete"

      - name: Comment Preview Link on PR
        uses: actions/github-script@v7
        with:
          script: |
            const prNumber = context.issue.number;
            const previewUrl = `https://docs.example.com/previews/pr-${prNumber}/`;
            github.rest.issues.createComment({
              issue_number: prNumber,
              owner: context.repo.owner,
              repo: context.repo.repo,
              body: `🚀 **Preview Deployment Ready!**\n\nPreview your changes here: [${previewUrl}](${previewUrl})`
            });
```

### 2. PR Cleanup Workflow (`.github/workflows/pr-cleanup.yml`)

Automatically clean up preview files when a Pull Request is closed or merged:

```yaml
name: Cleanup PR Preview

on:
  pull_request:
    types: [closed]

jobs:
  cleanup-preview:
    runs-on: ubuntu-latest
    steps:
      - name: Remove PR Preview Directory
        uses: appleboy/ssh-action@v1.0.3
        with:
          host: ${{ secrets.SERVER_IP }}
          username: ${{ secrets.DEPLOY_USER }}
          key: ${{ secrets.SSH_PRIVATE_KEY }}
          script: |
            rm -rf /srv/www/raknaDocs/previews/pr-${{ github.event.number }}
```
